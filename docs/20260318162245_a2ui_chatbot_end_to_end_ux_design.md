# A2UI Chatbot End-to-End UX 설계 문서

## 문서 목적

이 문서는 사용자가 A2UI를 처음 등록하고, 필요한 데이터를 연결하고, 미리보기로 검증한 뒤,
최종적으로 챗봇 안에서 실제 A2UI를 보게 되는 전체 end-to-end 경험을 설계한 문서다.

이 문서는 다음 질문에 답한다.

- A2UI를 처음 쓰는 설정자는 무엇을, 어떤 순서로 해야 하는가
- 설정 과정에서 막히는 지점 없이 어떻게 안내해야 하는가
- 챗봇 사용자는 어떤 순간에 A2UI를 보게 되는가
- preview, validation, publish, fallback은 어떻게 보여줘야 하는가
- 제품이 `생각 없이 써도 되는 수준`이 되려면 UX가 어떻게 설계되어야 하는가

---

## 1. 설계 목표

이 UX의 목표는 단순하다.

`설정자는 코드를 몰라도 A2UI를 등록하고 preview한 뒤 챗봇에 배포할 수 있어야 하고, 최종 사용자는 텍스트를 읽지 않아도 되는 순간에 자동으로 의미 있는 A2UI를 받게 해야 한다.`

세부 목표:

- 첫 등록 성공까지 15분 이하
- 최소 1개의 starter를 preview까지 완주
- 설정자는 “왜 이 템플릿이 선택되는지” 이해 가능
- 최종 사용자는 “챗봇이 적절한 UI를 띄워준다”는 인상을 받음
- 실패 시 원인과 수정 방법이 즉시 보임

---

## 2. 핵심 원칙

### 2.1 사용자는 A2UI 엔진을 배우면 안 된다

사용자는 `scene`, `binding`, `executor`를 이해할 필요가 없다.

사용자가 이해해야 할 개념은 다음 네 개뿐이다.

- 어떤 상황에 쓸지
- 어떤 템플릿을 쓸지
- 어떤 데이터를 연결할지
- preview가 잘 뜨는지

### 2.2 설정보다 preview가 먼저다

사용자는 설정 화면을 완성한 뒤 결과를 보는 게 아니라,
결과를 먼저 보면서 설정을 수정해야 한다.

즉 UX는 반드시 다음 순서를 가져야 한다.

`select -> connect -> preview -> fix -> save -> publish`

### 2.3 질문 의도와 템플릿 관계가 눈에 보여야 한다

이 제품은 결국 챗봇에서 동작하므로,
설정자는 항상 아래 질문에 답할 수 있어야 한다.

- 어떤 질문이면 이 템플릿이 뜨는가
- 어떤 문맥이면 템플릿이 선택되는가
- 어떤 데이터가 부족하면 fallback 되는가

### 2.4 실패는 숨기지 않는다

실패는 최소 3단계로 보여줘야 한다.

- 어떤 source 호출이 실패했는지
- 어떤 필드가 부족한지
- 그래서 최종적으로 어떤 fallback이 적용됐는지

### 2.5 publish 전에는 반드시 실제 챗봇처럼 테스트할 수 있어야 한다

설정자는 “이 템플릿이 실제 챗봇에서 어떻게 보일지”를
preview 전용 화면이 아니라 챗봇에 가까운 샌드박스에서 확인할 수 있어야 한다.

---

## 3. 사용자 유형

### 3.1 설정자

역할:

- 챗봇에 어떤 A2UI를 붙일지 정함
- 데이터를 연결함
- preview와 publish를 수행함

특징:

- 개발자가 아닐 수도 있음
- API 구조를 완벽히 알지 못할 수도 있음
- 빠르게 성공하고 싶어 함

### 3.2 최종 사용자

역할:

- 실제 챗봇 사용자
- 운영, 배포, 인시던트, 리포트 업무를 수행

특징:

- 설정 과정을 몰라도 됨
- 필요한 순간에 바로 A2UI를 보고 싶어 함

---

## 4. 전체 사용자 여정

전체 흐름은 다음 7단계로 구성한다.

1. A2UI 시작
2. Starter 선택
3. 데이터 연결
4. Validation & Preview
5. 질문/트리거 설정
6. Publish
7. 챗봇 사용

---

## 5. 단계별 UX 설계

## 5.1 A2UI 시작

### 목적

처음 들어온 사용자가 “여기서 뭘 해야 하는지”를 즉시 이해하게 만드는 단계다.

### 화면 구성

- 헤더: `A2UI Builder`
- 서브 문구: `챗봇에서 보여줄 운영 UI를 등록합니다`
- 시작 버튼: `새 A2UI 만들기`
- 최근 항목
- 추천 starter 3개

### 반드시 보여줘야 할 것

- 이 제품이 하는 일 한 줄 설명
- 시작 가능한 starter 예시
- 완료까지 필요한 단계 수

### 금지

- 첫 화면에서 source, binding, schema 같은 내부 개념 노출

---

## 5.2 Starter 선택

### 목적

설정자가 “어떤 문제를 해결하려는지” 기준으로 출발하게 만든다.

### 화면 구성

카탈로그 카드 형태:

- `Incident Triage`
- `Rollback Decision`
- `Execution Check`
- `Job Review`
- `Handoff Summary`
- `Report Draft`

각 starter 카드에는 다음이 있다.

- 이름
- 한 줄 설명
- 어떤 질문에 쓰는지
- 필요한 데이터 종류
- preview 썸네일

### 사용자가 하는 일

- 목적에 맞는 starter를 하나 선택

### 꼭 필요한 UX

- `이 starter는 보통 이런 질문에서 동작합니다`
- `이 starter는 이런 데이터가 필요합니다`

---

## 5.3 데이터 연결

### 목적

starter가 실제로 쓸 데이터를 연결하는 단계다.

### 화면 구성

좌측: starter summary  
우측: required slot 목록

예:

- `incident`
- `evidence`
- `events`
- `metrics`

각 slot마다 설정 폼:

- source type
  - internal DB
  - internal API
  - external HTTP
- method
- URL
- path params
- query params
- body params
- response path
- 필수/선택 표시

### 설정자가 하는 일

각 slot마다 다음을 입력한다.

- 어떤 endpoint를 쓸지
- 어떤 파라미터를 넣을지
- 응답에서 어느 부분을 쓸지

### 파라미터 입력 UX

직접 expression 문법을 쓰게 하면 안 된다.

대신 드롭다운 기반으로 제공한다.

예:

`id` 값의 출처:

- 선택된 엔티티 ID
- 현재 페이지
- 현재 사용자 ID
- 직접 입력
- 템플릿 인자

내부적으로는 `$context.selectedEntityId` 같은 표현식이 되더라도,
설정자는 그걸 몰라도 된다.

### 필수 보조 기능

- 샘플 응답 보기
- 최근 성공 응답 보기
- source 테스트 버튼

---

## 5.4 Validation & Preview

### 목적

설정이 실제로 동작하는지 바로 검증하는 단계다.

### 화면 구성

3단 분할이 가장 좋다.

1. Raw Response
- 실제 API 응답

2. Bound Data
- template slot에 연결된 결과

3. Final A2UI Preview
- 실제 렌더 결과

### 꼭 필요한 메시지

- 성공
  - `preview 성공`
- 부분 성공
  - `필수 데이터 일부 누락`
- 실패
  - `response path가 잘못되었습니다`
  - `incidentId 파라미터가 비어 있습니다`
  - `output schema가 예상과 다릅니다`

### 사용자가 하는 일

- source 실행
- 응답 확인
- binding 결과 확인
- A2UI preview 확인
- 문제 있으면 source/binding 수정

### 이 단계에서 꼭 보여줘야 할 것

- 어떤 slot이 채워졌는지
- 어떤 slot이 비어 있는지
- fallback이 적용됐는지
- 최종 챗봇에서 어떤 형태로 보일지

---

## 5.5 질문/트리거 설정

### 목적

챗봇이 언제 이 A2UI를 띄울지를 정의하는 단계다.

### 화면 구성

- 추천 질문 예시
- 키워드 기반 트리거
- 페이지 기반 트리거
- 역할 기반 트리거
- 우선순위

### 설정자가 하는 일

- 어떤 질문이면 이 템플릿을 띄울지 정함
- 어느 페이지에서만 동작할지 정함
- 어느 역할에서 허용할지 정함

### 테스트 UX

“질문 시뮬레이터”가 있어야 한다.

예:

- 입력: `이 배포 롤백해야 해?`
- 결과:
  - 선택된 템플릿: `Rollback Decision`
  - 이유
  - 필요한 데이터
  - preview

---

## 5.6 Publish

### 목적

설정 완료된 A2UI를 실제 챗봇 환경에 반영하는 단계다.

### 화면 구성

- publish 전 체크리스트
- 변경 요약
- 대상 환경
- 최종 테스트 결과
- publish 버튼

### 반드시 보여줘야 할 것

- 어떤 starter가 배포되는지
- 어떤 질문에서 트리거되는지
- 필수 source가 모두 정상인지
- fallback 정책이 무엇인지

### publish 후

- 성공 배너
- 챗봇 샌드박스로 이동 버튼
- 실사용 로그 보기 버튼

---

## 5.7 챗봇 사용

### 목적

최종 사용자가 실제 챗봇에서 A2UI를 소비하는 단계다.

### 최종 사용자 경험

사용자는 그냥 질문한다.

예:

- `이 장애 원인 비교해줘`
- `이 배포 rollback 해야 해?`
- `이 job 실행 전에 확인할 것 보여줘`

챗봇은:

1. 질문 의도 파악
2. 현재 페이지/선택 엔티티 확인
3. 해당 starter/template 선택
4. source 실행
5. A2UI 렌더

즉 최종 사용자는 설정을 몰라도 되고,
적절한 순간에 텍스트 대신 A2UI를 보게 된다.

---

## 6. 실패 시 UX

이 문서에서 실패 UX는 빠질 수 없다.

### 6.1 Source 실패

표시:

- 어떤 source가 실패했는지
- endpoint가 무엇인지
- 에러 사유

액션:

- 다시 테스트
- response path 수정
- 파라미터 소스 수정

### 6.2 필수 데이터 누락

표시:

- 어떤 slot이 비었는지
- 왜 필수인지
- fallback 결과가 무엇인지

### 6.3 Trigger mismatch

표시:

- 질문은 들어왔지만 템플릿이 선택되지 않은 이유
- 키워드 부족 / 페이지 불일치 / 역할 불일치

### 6.4 Publish 차단

필수 source 하나라도 깨져 있으면 publish 불가

---

## 7. “부족한 것이 단 하나도 없게” 만들기 위한 필수 보조 기능

다음은 선택이 아니라 필수다.

### 7.1 Starter 추천

사용자가 무엇을 골라야 할지 모를 때 추천 starter가 떠야 한다.

### 7.2 샘플 응답 기반 미리보기

실제 API 연결 전에도 샘플 JSON으로 preview 가능해야 한다.

### 7.3 질문 시뮬레이터

질문을 넣으면 어떤 template가 선택되는지 보여줘야 한다.

### 7.4 Diffable publish

수정 전/후 어떤 설정이 바뀌는지 보여줘야 한다.

### 7.5 Runtime diagnostics

실사용 중 어떤 source가 자주 실패하는지 보여줘야 한다.

### 7.6 Fallback visibility

최종 사용자가 partial/fallback 상태를 인지할 수 있어야 한다.

### 7.7 Audit trail

누가 어떤 A2UI를 publish했고, 어떤 설정을 바꿨는지 남아야 한다.

---

## 8. 시스템 관점의 최소 구현 순서

이 UX를 실제로 만들려면 구현 순서는 다음이 적절하다.

1. starter/template catalog
2. source registration form
3. binding form
4. preview/test API
5. template selection simulator
6. publish flow
7. chatbot runtime integration
8. diagnostics/audit

---

## 9. 성공 기준

이 UX가 성공했다고 판단하려면 최소 다음이 만족돼야 한다.

- 처음 쓰는 설정자가 starter 하나를 preview까지 완주 가능
- 설정자는 코드 없이 source 연결 가능
- preview에서 문제 원인을 즉시 이해 가능
- publish 후 챗봇에서 실제 A2UI가 뜸
- 최종 사용자는 텍스트 대신 A2UI가 나오는 이유를 자연스럽게 이해함

---

## 10. 한 줄 결론

`A2UI의 end-to-end UX는 “템플릿 선택 -> 데이터 연결 -> preview -> 트리거 설정 -> publish -> 챗봇 사용”의 6단 구조로 설계되어야 하며, 사용자는 내부 엔진 개념을 몰라도 되고, 설정자는 미리보기와 검증을 통해 끊김 없이 성공 경험에 도달해야 한다.`
