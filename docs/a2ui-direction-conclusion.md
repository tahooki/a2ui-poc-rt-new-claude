# A2UI 방향성 결론 정리

## 문서 목적

이 문서는 A2UI를 앞으로 어떤 제품 형태로 개발해야 하는지에 대해 나눈 논의를 정리한 결론 문서다.

이 문서는 특히 다음 질문에 대한 결론을 고정한다.

- A2UI는 제3자가 직접 조합하는 범용 라이브러리인가
- A2UI는 scene 중심으로 가야 하는가, template 중심으로 가야 하는가
- 제3자가 실제로 이 구조를 사용할 수 있는가
- 데이터를 누가, 어떻게 연결해야 하는가
- 앞으로 어떤 방향으로 개발해야 하는가

---

## 1. 논의 배경

초기에는 A2UI를 제3자가 직접 조합하는 범용 라이브러리 또는 플랫폼처럼 제공할 수 있을지, 그리고 그 구조가 `scene` 중심이어야 하는지 `template` 중심이어야 하는지를 논의했다.

대화를 진행하면서 다음 현실 조건이 더 중요하다는 결론에 도달했다.

- 제3자가 capability, semantic mapping, scene planner까지 직접 이해하고 설정하는 방식은 진입장벽이 높다.
- 제3자는 자기 서비스의 핵심 기능과 버그 대응도 바쁜 상황이기 때문에, 챗봇용 UI를 만들기 위해 별도 통합 프로젝트 수준의 작업을 하려 하지 않을 가능성이 높다.
- `API를 연결하고 A2UI를 직접 조합하는 플랫폼`은 기술적으로 가능하지만, 실제 채택 가능성은 낮다.

---

## 2. 핵심 결론

### 2.1 제품의 본질

A2UI는 `제3자가 직접 조합하는 범용 UI builder`보다는,

`특정 서비스에 챗봇을 붙였을 때, 적절한 운영 UI를 자동으로 제공하는 Chatbot-native augmentation layer`

로 정의하는 것이 더 현실적이다.

즉 사용자는 거의 생각하지 않고 써야 하며, 우리가 대상 서비스와 데이터 연동, A2UI 구성, 정책, UX를 미리 설계해 두는 방향이 맞다.

---

## 3. Scene vs Template 결론

### 3.1 현재 가정 하에서의 판단

현재 가정은 다음과 같다.

- 우리가 타겟 서비스를 먼저 파악한다.
- 우리가 필요한 API 권한과 데이터 접근을 확보한다.
- 우리가 데이터 바인딩 방식을 설계한다.
- 우리가 챗봇 문맥에 맞는 A2UI를 미리 설계한다.
- 사용자는 별도 설계 없이 그냥 사용한다.

이 가정이라면 `scene`보다 `template`가 더 적합하다.

### 3.2 이유

템플릿 중심 구조의 장점:

- 결과 예측이 쉽다
- QA와 운영이 쉽다
- 서비스별 최적화가 쉽다
- 데이터 요구사항을 명확히 정의할 수 있다
- 제품 설명이 쉽다

반면 scene 중심 구조는 다음 상황에서 강하다.

- 다양한 도메인에 범용적으로 붙여야 할 때
- 런타임 조합이 핵심일 때
- 외부 사용자가 직접 확장해야 할 때

하지만 현재는 그보다 `관리형 제품 경험`이 더 중요하므로, 주된 제품 구조는 템플릿 중심이 맞다.

### 3.3 다만 순수 고정 템플릿만으로는 부족함

템플릿만으로 가면 자유도가 너무 낮아질 수 있으므로, 최종 방향은 다음이 적절하다.

`고정 목적과 안전성은 템플릿으로 관리하고, 내부 section/강조/우선순위는 제한적으로 동적으로 조합하는 방식`

즉 완전 자유 scene도 아니고, 완전 고정 카드도 아닌 `guided dynamic template` 구조가 적합하다.

---

## 4. 데이터 연동에 대한 결론

### 4.1 제3자가 직접 설계하는 구조는 비현실적임

처음에는 제3자가 자기 서비스 API를 등록하고 capability를 정의해 A2UI를 조합하는 구조를 생각했지만, 실제 채택 가능성이 낮다는 결론에 도달했다.

이유:

- 데이터 연결 방식이 복잡하다
- semantic mapping과 capability 개념이 어렵다
- 결과 예측이 어렵다
- integration effort가 크다

### 4.2 현실적인 방향

우리가 직접 다음을 한다.

- 대상 서비스 파악
- 필요한 API/권한 확보
- 데이터 바인딩 구조 설계
- 질문 의도와 A2UI 매핑 설계
- 서비스별 의미 있는 A2UI 템플릿 설계

즉 외부 사용자는 API 구조나 A2UI 조합 방식을 깊게 알 필요가 없어야 한다.

---

## 5. 제3자 사용성과 채택에 대한 결론

### 5.1 제3자는 복잡한 시스템을 잘 쓰지 않음

다음과 같은 시스템은 대부분 자발적으로 사용하지 않을 가능성이 높다.

- capability를 직접 정의해야 함
- scene/planner를 이해해야 함
- semantic mapping을 해야 함
- 실패 원인을 직접 추적해야 함

### 5.2 제3자가 실제로 쓰게 하려면

반드시 다음 조건이 필요하다.

- 설정이 거의 없어야 함
- 첫 성공 경험이 빨라야 함
- `이걸 쓰면 어떤 UI가 나오는지` 바로 보여줘야 함
- 실패 이유가 설명 가능해야 함
- ROI가 분명해야 함

하지만 현재 결론은, 아예 그 부담을 사용자에게 넘기지 않고 우리가 먼저 설계해 두는 managed 방향이 더 적합하다는 쪽이다.

---

## 6. 최종 제품 방향

최종적으로 A2UI는 다음 성격을 가진다.

- 범용 조립형 플랫폼이 아님
- 챗봇 확장 레이어임
- 특정 서비스/도메인에 맞춰 미리 설계된 운영형 UI 집합임
- 사용자는 문맥에 맞는 A2UI를 거의 자동으로 받음
- 내부적으로는 일부 scene/section 재사용 구조를 가질 수 있지만, 외부 제품 개념은 템플릿 중심이어야 함

---

## 7. 앞으로의 개발 방향

앞으로 개발은 다음 순서로 가는 것이 맞다.

### 7.1 타겟 서비스군 정의

- 어떤 서비스에 붙일지 정한다

### 7.2 서비스별 핵심 사용자 질문과 워크플로우 정리

- 어떤 질문이 들어오고
- 어떤 순간에 A2UI가 필요해지는지 정의한다

### 7.3 서비스별 데이터/API 연동 설계

- 필요한 API
- 인증 방식
- 응답 구조
- 가공 방식 정의

### 7.4 서비스별 기본 A2UI 템플릿 설계

- 예: 요약, 비교, 검토, 승인 전 확인, 실행 추적, 핸드오프

### 7.5 챗봇 질문 의도와 템플릿 매핑 설계

- 어떤 질문이면 어떤 A2UI가 나와야 하는지 명확히 정의

### 7.6 내부 공통 재사용 레이어 정리

- 공통 block
- 공통 정책
- 공통 renderer
- 필요 시 scene-like abstraction 유지

---

## 8. 요약 결론

한 줄로 요약하면 다음과 같다.

`A2UI는 제3자가 직접 설계하고 조합하는 범용 라이브러리보다, 우리가 대상 서비스와 데이터 연동을 먼저 설계하고 챗봇 문맥에 맞는 A2UI를 자동으로 제공하는 관리형 템플릿 제품으로 가는 것이 더 현실적이다.`

그리고 구조적으로는 다음이 가장 적합하다.

`외부 제품 경험은 템플릿 중심, 내부 구현은 제한적 동적 조합을 허용하는 guided dynamic template 구조`
